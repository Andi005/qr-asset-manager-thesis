# Requirements

**Status:** derived from the approved proposal ([proposal.md](../proposal/proposal.md)) and implemented in full. Each requirement has an ID, used in [traceability.md](traceability.md), in tests and in the thesis.

Sources: **O2-O4** = proposal objectives 2-4; **§5** = evaluation; **§7** = scope.

## Functional requirements
| ID | Requirement | Source |
|---|---|---|
| FR-01 | Register a hardware asset. The tag (`IT-000123`) is generated by the system, unique and never changed. Fields: category, manufacturer, model, serial number (optional, unique when present), purchase date, warranty end date, location, status, notes. | O3 |
| FR-02 | List, search and filter assets by tag, serial number, model, status and location. | O3 |
| FR-03 | Edit an asset. A retired asset stays in the records (no deletion). Two people editing the same asset at once must not silently overwrite each other. | O3 |
| FR-04 | Manage employees (the people who hold assets) and locations. Employees are deactivated, not deleted. | O3 |
| FR-05 | Assign an asset to an employee and return it. An asset has at most one holder at a time. Retired or in-repair assets and inactive employees can't receive assignments. | O3 |
| FR-06 | Show the full assignment history of an asset and of an employee: who had which asset, from when to when. | O3, §1 |
| FR-07 | Keep a change history: who changed what on an asset or license, and when. | §1 (problem), O3 |
| FR-08 | Register software licenses: name, vendor, number of seats, expiry date (or perpetual). | O3 |
| FR-09 | Allocate a license seat to an employee or an asset, and release it. Never exceed the number of seats. | O3 |
| FR-10 | Track warranties through each asset's warranty end date. | O3 |
| FR-11 | Show licenses and warranties expiring within 90 days (today to today+90, inclusive), and those already expired, on one view and the dashboard. | O3, §5 task 3 |
| FR-12 | Access roles: ADMIN (users, import, everything), IT_STAFF (manage assets, licenses, assignments, labels, inventory), VIEWER (read-only). All pages need a login. | O3 |
| FR-13 | Import existing asset records from a CSV file (exported from Excel). Report every invalid row with its line and reason. Import nothing until the file is valid. | O3 |
| FR-14 | Generate and print QR labels for selected assets. Each label holds the asset's URL and shows the tag as text. | O4 |
| FR-15 | Scan a label from a phone browser (no native app) and open the asset's record. | O4, §7 |
| FR-16 | Inventory session: choose a location or a list of expected assets; scan; record each scan with a timestamp; show found, missing and unexpected assets and the total duration; export to CSV. | §5 (P2) |

## Non-functional requirements
| ID | Requirement | Source |
|---|---|---|
| NFR-01 | The user interface is in Albanian, with all texts in message files. | context |
| NFR-02 | The scanning flow is usable on a phone (portrait, large controls); it works in current Chrome (Android) and Safari (iOS). | O4 |
| NFR-03 | Served over HTTPS in production (phone browsers allow the camera only on secure origins). | O4 |
| NFR-04 | Security basics: hashed passwords, CSRF protection, role checks on the server, input validation, no secrets in the code, configuration through environment variables. | O3 |
| NFR-05 | Data integrity rules are enforced by the database as well (unique tag, one open assignment per asset, seat rules). | O2 |
| NFR-06 | Database changes only through versioned migrations. | O2 |
| NFR-07 | Main pages answer within 1 second with about 1,000 assets on the free hosting tier (after warm-up). | evaluation practicality |
| NFR-08 | Runs from a fresh clone with Docker (`docker compose up`); deployable as one Docker image. | O3 |
| NFR-09 | Automated tests for every business rule, and CI on every change. | quality |
| NFR-10 | QR labels contain no personal or secret data. Only the data needed for asset tracking is stored about employees. | privacy |

## Scope decisions
- **Out of scope (§7):** native mobile app, procurement and purchasing, integration with university systems, automatic network discovery, financial depreciation.
- **Excel import is via CSV:** users save the Excel sheet as CSV ("Save as → CSV UTF-8"). Reading `.xlsx` directly is left out to keep the build within time. It's a limitation to name in the thesis.
- Reading `.xlsx` directly and e-mail reminders for expiring items are possible future work.

## Assumptions
No requirements interview with a real IT office was carried out for this build. The requirements come from the approved proposal and from the following working assumptions, which are **not** interview findings and must not be presented as such:
- Three roles (ADMIN, IT_STAFF, VIEWER) are enough for a small IT unit.
- About 1,000 assets is a realistic upper bound for performance (NFR-07).
- Exporting the existing Excel sheet as CSV is an acceptable import path.
- Labels must carry no personal data, and opening a label must require a login.
